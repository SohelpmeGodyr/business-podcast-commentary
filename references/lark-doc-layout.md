# 飞书商业评述版式参考

仅当商业评述需要写入飞书云文档或 Wiki 文档时读取本文件。具体 XML 语法、可用属性和创建/更新命令以 `lark-doc` 的说明为准。

## 版式目标

让没有听过原节目的人先建立上下文，再理解判断和机制，最后核查证据与行动项。使用结构和视觉编码降低跳读成本，不把文档做成海报、来源堆栈或组件展览。

## 推荐信息架构

1. `<title>` + 元数据：标题、来源、嘉宾角色、日期、时长与资料边界。
2. 摘要与阅读导向：约 300—500 个中文字，先说明聊了什么、论证主线和证据边界。
3. “这期到底讲了什么”：用 3—7 个连续要点或短段落还原讨论路径。
4. 主题正文：先交代背景和嘉宾论证，再给编辑分析；用 `h1` / `h2` 支持跳读。
5. 商业机制、赢家、约束与风险：只在关系复杂时使用图示或表格。
6. 隐性信号与后续观察：跨段隐性信号集中呈现，观察项用 `<checkbox>` 或简表。
7. 事实核查与证据台账：放在正文末尾；正文只保留必要的短状态和编号。
8. 原始逐字稿：全文展开，置于最末。

## 组件选择

| 信息类型 | 首选组件 | 使用提醒 |
|---|---|---|
| 核心编辑判断、关键风险、待验证项 | `<callout>` | 每个 callout 只承载一种语义。 |
| 两组短观点的并列比较 | `<grid>` + 两个 `<column>` | 优先双栏；内容较长时改为小标题或表格。 |
| 数字口径、利益相关方、情景矩阵 | `<table>` | 首行作为表头；避免用表格装段落。 |
| 观察项、行动项 | `<checkbox>` | 适合可检查、可更新的条目。 |
| 因果链、价值链、飞轮、流程、时间线 | Mermaid 或 SVG 画板 | 只保留正文难以高效表达的关系。 |
| 来源入口 | 链接预览、书签或引用 | 来源说明应可追溯，不堆砌链接。 |

## 混合标注

- 文档靠前位置提供一次简短“阅读标记”，用普通话解释“某某的说法”“某某透露，暂时查不到公开证据”“我们的判断”“隐性信号”和事实状态；后文不重复长解释。
- 嘉宾观点：整段使用 `light-blue` callout，emoji 使用 `🎙️`，成文写“Kevin 的说法”。这表示嘉宾的观点，不是外部确认，也不是编辑结论。
- 公司内部信息：整段使用 `light-yellow` callout，emoji 使用 `🏢`，成文写“Kevin 透露，暂时查不到公开证据”。不要使用绿色背景。
- 编辑分析：整段使用 `light-gray` callout，emoji 使用 `📝`，成文写“我们的判断”。禁止只把标签加粗后接在普通正文中。
- 隐性信号：整段使用 `light-yellow` 或 `light-gray` callout，emoji 使用 `💧`，标题必须出现“隐性信号”和 I 编号。正文用“也可能是另一种情况”“怎么判断”，不展示“反方解释”“可证伪条件”等内部术语。
- 会立即改变当前段落含义的错误、重大存疑或口径差异：原话后另起一段，用一句彩色短提示说明状态、差异和编号。
- 一般核查：正文只放短标签与编号；完整原话、来源、搜索过程和局限放在文末一次呈现。
- 与单段强相关的高价值隐性信号：使用一个简短 callout；跨多个段落才成立的信号放入“综合推演”。
- 同一内容不在正文和附录完整重复。连续出现多个 callout 时，优先合并或改回普通段落。
- 长引语只在措辞本身具有分析价值时使用；其余采用忠实转述并保留时间戳。

## 颜色语义

| 语义 | 推荐颜色 | 辅助编码 |
|---|---|---|
| 范围、定义、编辑说明 | 蓝色 / `light-blue` | ℹ️、说明文字 |
| 已验证事实、正向建议 | 绿色 / `light-green` | ✅、来源或依据 |
| 假设、待确认、观察项 | 黄色 / `light-yellow` | ❗、待验证标签 |
| 风险、反例、失效条件 | 红色 / `light-red` | ⚠️、条件说明 |
| 背景、补充材料 | 灰色 / `light-gray` | 辅助文字 |
| 隐性信号 | 证据较强：黄色 / `light-yellow`；信息仍不足：灰色 / `light-gray` | 💧、标注“隐性信号”和 I 编号 |
| 嘉宾观点 | 蓝色 / `light-blue` | 🎙️、嘉宾姓名、标注“某某的说法” |
| 公司内部信息 | 黄色 / `light-yellow` | 🏢、标注“暂时查不到公开证据” |
| 编辑分析 | 灰色 / `light-gray` | 📝、标注“我们的判断” |

使用颜色时，同时写明语义或方向。例如关键指标除红绿外，同步使用 ↑、↓、+/- 或“上升/下降”。

核查状态文字分别使用 `<span text-color="green">`、`<span text-color="orange">` 或 `<span text-color="red">`；不用 CSS、`style` 或十六进制色码。嘉宾判断、一手陈述和编辑分析不使用核查颜色。

F 编号按正文第一次出现的顺序分配；附录专有条目排在正文条目之后。首个可见编号必须是 F-01，全文连续，正文和附录一致。

## 飞书文档完成前检查

- 首屏是否在 30 秒内让陌生读者知道谁在讲、聊了什么、为何值得读和证据边界？
- 标题层级是否能支持快速跳读？
- 每一种组件是否都减少了理解成本？
- 颜色是否始终表达同一语义，并有文字或 emoji 辅助？
- 图示是否承载关键关系，而非复述段落？
- 正文是否先完成内容还原，再进入编辑判断？
- 一般核查是否只显示短标签，完整证据仅在文末出现一次？
- 嘉宾主张、内部陈述、编辑分析是否整段高亮并能一眼区分，而不是只加粗四个字？
- 第一次出现的事实编号是否为 F-01，后续是否按正文顺序连续？
- callout、长引语和表格是否少量使用，没有连续打断阅读？
- 现有文档的内容、资源块和原有风格是否得到保留？
