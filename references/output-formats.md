# 多格式交付规范

本文件只负责把同一份商业评述映射为不同文档格式。内容覆盖、事实核查和编辑推演规则以 `SKILL.md` 为准，不能因为换格式改变结论或减少必要上下文。

## 格式选择

1. 用户指定格式时严格遵循。
2. 用户要求更新已有文档时沿用该文档格式和既有风格。
3. 用户未指定时输出标准 Markdown `.md`，兼容 Obsidian 和普通 Markdown 阅读器。
4. 用户同时要求多种格式时，先确定一份内容母版，再分别渲染；核对标题、段落、编号、链接、表格和逐字稿是否一致。

输入来源不自动决定输出格式：飞书逐字稿可以输出为 Word 或 Markdown，本地逐字稿也可以写入飞书，但外部写入必须得到用户明确授权。

## 共同视觉层级

所有格式都区分以下四类对象：

| 对象 | 必须出现的文字标记 | 视觉原则 |
|---|---|---|
| 嘉宾原意 | “某某的说法”、忠实转述或原话时间戳 | 普通正文或引用，不用核查颜色。 |
| 事实状态 | 已确认 / 部分确认 / 无法验证 / 存疑 + F 编号 | 简短醒目，详细证据只在文末展开一次。 |
| 编辑判断 | “我们的判断” | 与嘉宾观点分段，不伪装成事实。 |
| 隐性信号 | “隐性信号” + I 编号 | 少量使用，用大白话说明理由、另一种可能和判断方法。 |

标题层级、章节顺序和编号在不同格式之间保持一致。颜色和 emoji 只是辅助；去掉颜色后，读者仍应能理解状态。

内部仍可使用“嘉宾判断 / 一手陈述 / 编辑分析 / 编辑推演”等分类；成文优先显示“某某的说法”“某某透露，暂时查不到公开证据”“我们的判断”“隐性信号”。视觉样式必须覆盖整个语义段落，而不是只加粗标签。一个段落混合不同身份时先拆段。读者可见的 F 编号按正文首次出现顺序分配；仅附录出现的事实接在正文事实之后。

## Markdown 与 Obsidian

### 标准 Markdown

- 使用 `#`—`###`、普通段落、`>` 引用、列表、标准 Markdown 表格和可点击链接。
- 状态写成粗体短标签，例如：`**🔴 存疑（F-04）**：公开数据与原话口径矛盾，详见文末。`
- 嘉宾观点使用引用块并以 `**🎙️ Kevin 的说法：**` 开头；公司内部信息使用引用块并以 `**🏢 Kevin 透露，暂时查不到公开证据：**` 开头。
- 编辑分析使用引用块并以 `**📝 我们的判断：**` 开头，使整段与普通内容分开；不要只加粗标签，也不要用 HTML 颜色。
- 隐性信号使用引用块并以 `**💧 隐性信号 I-02｜一句话结论：**` 开头。内部的“反方解释 / 可证伪条件”改写成“也可能是另一种情况 / 怎么判断”。
- 完整逐字稿使用二级标题置于最末并全文展开，不用 `<details>` 折叠。

### Obsidian 增强

仅当用户明确要求 Obsidian 版时，可使用 callout；正文主体仍使用普通段落，避免每一段都变成卡片。

```markdown
> [!warning] 存疑 F-04
> 公开数据与该原话的排名口径矛盾，完整来源见文末。

> [!note] 隐性信号 I-02｜一句话结论
> 为什么这样判断、也可能是另一种情况、接下来怎么判断。

> [!info] Kevin 的说法
> 嘉宾的判断，不代表已经得到外部确认。

> [!abstract] 我们的判断
> 编辑基于材料形成的解释，不是嘉宾原话。
```

- `note`：编辑说明；`warning`：存疑或风险；`question`：无法验证；`info`：一般证据状态。
- YAML 属性只在用户已有知识库规范或明确要求时添加，不擅自发明标签、别名或目录结构。
- 内链只有在目标笔记实际存在时使用；外部来源继续使用标准 URL。

## Word `.docx`

创建或编辑 Word 文档时使用可用的 `documents` 技能及其运行时，不把 Markdown 或飞书 XML 直接改后缀伪装成 `.docx`。

- 标题使用 Word `Title`，章节使用 `Heading 1`—`Heading 3`，标题保持黑色并依靠字号、字重和留白建立层级。
- 正文使用连贯普通段落；嘉宾原话使用引用样式或缩进段落。
- 事实状态以粗体文字开头，例如“存疑（F-04）”，可使用克制的文字颜色，但不能只靠颜色传达结论。
- “某某的说法”“某某透露，暂时查不到公开证据”“我们的判断”和“隐性信号”使用独立段落样式、左侧边线、浅底纹或段前标签之一，确保整个语义段落可辨；不使用高饱和彩色文本框或连续装饰卡片。
- 表格只用于确实需要横向比较的数据；设置合理列宽、自动换行和清晰表头，不把长篇分析塞进单元格。
- 全文逐字稿置于最后一个一级章节；长文可加目录，但不隐藏或折叠正文。

每次生成或实质修改 `.docx` 后都必须：

1. 使用文档技能规定的渲染器输出逐页 PNG；
2. 逐页检查中文字体、标题层级、表格换行、分页、引用缩进、链接和全文逐字稿；
3. 修复后重新渲染，直到没有裁切、重叠、缺字、异常留白或断裂表格；
4. 只交付最终 `.docx`，不把 QA 图片作为默认附件。

## 飞书文档

需要飞书交付时先读取 `lark-doc` 的认证、XML、样式及创建或更新工作流，再读取 [lark-doc-layout.md](lark-doc-layout.md)。

- 状态文字分别使用 `<span text-color="green">`、`<span text-color="orange">` 或 `<span text-color="red">`；不用 CSS 或十六进制色码。
- 一般核查只放状态与编号，完整核查在文末出现一次。
- 文档靠前位置用一个简短 callout 解释阅读标记。成文标签优先写“Kevin 的说法”“Kevin 透露，暂时查不到公开证据”“我们的判断”“隐性信号”。分别使用浅蓝、浅黄、浅灰、浅黄或浅灰 callout。样式覆盖整段，不只覆盖标签。
- F 编号按正文首次出现顺序连续分配，正文第一条必须是 F-01；附录条目与正文完全同步。
- callout、grid、表格和画板仅在降低理解成本时使用，不为“丰富”强行添加。
- 逐字稿原文在文末全文展开，不使用默认收起的折叠块。

逐字稿本身是飞书文档且用户明确要求更新源文档时，评述插在逐字稿之前并保留原有素材；否则新建文档或交付用户指定的其他格式。

## 交付前跨格式检查

- 陌生读者是否能在目标文件中顺畅完成从内容还原到商业分析的阅读路径？
- 四类对象是否仅凭文字标记就能区分？
- 正文是否只保留必要的核查短提示，详细来源是否只出现一次？
- 标题、F/I 编号、链接、表格和逐字稿是否完整？
- 是否使用了目标编辑器真实支持的语法，而不是把另一种格式的标签原样复制过去？
